# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`hc` (handcoding) is a Go CLI/TUI that judges LeetCode-style problems locally: users write solutions in their own editor, and `hc` builds, runs and judges them offline, debugs them with Delve/pdb, fetches problems from LeetCode, and delegates test-case authoring to coding agents (Claude Code / Codex). User-facing docs are in English (`README.md`, `docs/`, `CONTRIBUTING.md`); `README_zh.md`, `docs/how-to-use_zh.md` and `docs/protocol_zh.md` mirror them in Chinese; update both languages together.

## Commands

```sh
make build            # bin/hc (version from git describe via -ldflags)
make install          # go install into $(go env GOBIN)
make test             # go test -race ./...
make lint             # go vet + golangci-lint (CI pins v2.15.0, see .github/workflows/ci.yml)

go test ./internal/app -run 'TestBuiltinReferences/two-sum' -v   # one subtest
go run ./cmd/hc -w /tmp/hc-dev test two-sum                       # run against a scratch workspace
```

- Integration tests in `internal/app` and `internal/tui` actually compile and run solutions; they need `go` and `python3` (3.10+) on PATH and skip otherwise.
- Go ≥ 1.26 is required (`errors.AsType` is used); `go.mod` pins the toolchain version.
- Use a throwaway workspace while developing (`hc init /tmp/hc-dev`, then `-w` or `HC_WORKSPACE`) instead of the user's `~/handcoding`.

## Architecture

Request flow: `internal/cli` (cobra) or `internal/tui` (bubbletea) → `internal/app` (use cases; the only layer both front ends call) → `internal/runner` → a `lang.Language` driver → `internal/judge`.

**Problem protocol** (`internal/problem`, spec in `docs/protocol.md`). A problem is a directory with `problem.yaml` (signature + judge options), `description.md`, `cases.jsonl`, optional `reference/solution.{py,go}` and `templates/`. Types reuse LeetCode's `metaData` names (`integer[]`, `ListNode`, `TreeNode`, `list<T>` normalized to `T[]`) so `internal/leetcode` can import questions without translation. Kinds: `function` and `class` (design problems driven by `ops`/`args`). `judge.output` names the parameter to judge for in-place (`void`) problems, and `judge.output_length: return` limits it to the first k elements. `judge.compare` has no default: without it a problem is *not ready* (`Problem.Ready`): `hc submit` refuses, and `hc test` shows outputs with the `NotJudged` verdict. `hc fetch` deliberately leaves it unset, because deciding the judge rule means reading the statement, and that is `hc gen`'s job (the skill's "decide the judge rule" step).

**Driver protocol** (`internal/lang/lang.go`). Language drivers never judge. They read `HC_CASES` (JSON array of `{id,input}`), call the user's code, and append `{id,output,error,elapsed_ns}` lines to `HC_OUT`. All comparison (exact / unordered / unordered_deep / any_of / float tolerance) happens in `internal/judge` on decoded JSON. User stdout/stderr pass through untouched. Missing result lines become RE or TLE in `runner.Run`. Adding a language = implement `lang.Language` and register it in `app.Languages`. Each driver declares `MinVersion`, the oldest toolchain the protocol supports (Python 3.10, Go 1.22): generated code, built-in references and pack content must work on it, user code need not. Below it, `hc test`/`submit`/`debug` warn and reference runs (`cases build`, `validate --run`) fail; CI runs Python 3.10 and `TestGoMinimumVersion` vets the Go side at `go 1.22`.

- **Go** (`internal/lang/golang`): each solution dir is a standalone module. `zz_hc_driver.go` = static `runtime.go.txt` (ListNode/TreeNode, codecs, main loop, nil-slice normalization) + per-problem `hcCall` generated from the signature. It sits next to `solution.go` so gopls and Delve breakpoints work on the user's real file.
- **Python** (`internal/lang/python`): `hc_runtime.py` (embedded, must stay Python 3.10 compatible) plus a generated `_hc_runner.py` that embeds the signature as JSON.
- Driver files are regenerated by `Prepare` before every run; never hand-edit them in a workspace.

**Workspace** (`internal/workspace`): `hc.yaml`, `problems/<NNNN-slug>/`, `solutions/<lang>/<NNNN-slug>/`, `.hc/hc.db`. Discovery order is `-w`, `$HC_WORKSPACE`, nearest parent containing `hc.yaml`, then `~/handcoding`.

**History** (`internal/store`): SQLite via `modernc.org/sqlite` (pure Go, no cgo). `submissions.details` holds the judge report encoded by `app.EncodeReport`. Failing cases are stored with truncated input/output so the TUI can re-render them later.

**Expected outputs come from reference solutions, not from the model.** `hc cases build` runs `reference/solution.*` through the same runner and writes outputs into `cases.jsonl`. `hc gen` / `hc fix` (`internal/agent`) run `claude -p` / `codex exec` as subprocesses in the workspace. Their prompt points at the skill in `internal/builtin/skill/SKILL.md`, which `hc init` / `hc skill install` copy into the workspace as `.claude/skills/handcoding/SKILL.md` and `AGENTS.md`. Keep that skill in sync with protocol and CLI changes, because agents follow it literally.

**TUI** (`internal/tui`): a screen stack (`list → detail → result`, `history → submission`). Test and submit run in a background `tea.Cmd`. Only the editor and the debugger take over the terminal (`tea.ExecProcess` / `clearScreenCmd`). The markdown theme must be detected before `tea.NewProgram` starts (`ui.DetectTheme`). Once bubbletea owns stdin, the terminal's background-color reply is swallowed and every render stalls until timeout. `ui.Markdown` caches renderers and output.

**Statement images** (`internal/termimg`): `hc fetch` downloads images into the problem's `assets/`. `ui.Markdown` swaps each `![](...)` for a token, lets glamour render, then replaces the token line with the image drawn as plain text lines. Because the image is ordinary lines of text, it scrolls inside a viewport. With kitty (kitty, Ghostty, and herdr, which re-emits kitty graphics to the outer terminal) those lines are Unicode placeholder cells for an image uploaded once with `q=2`; a reply would arrive as keystrokes. Detection is by environment only: herdr answers graphics queries itself and WezTerm answers them without supporting placeholders, so querying would mislead. With blocks, they are mosaic block characters. After the editor or debugger has used the terminal, `Renderer.Forget` forces a re-upload. Never query the terminal for graphics support once the TUI is running.

## Built-in sample problems

`internal/builtin/_problems/` is embedded into the binary. The leading underscore keeps the Go tool from compiling the `reference/*.go` files inside it. `TestBuiltinReferences` requires every case to have an expected output, and requires both the Python and the Go reference to pass. After changing those cases, regenerate expected outputs through a scratch workspace that symlinks the directory:

```sh
hc init /tmp/hc-bi --no-samples && rmdir /tmp/hc-bi/problems
ln -s "$PWD/internal/builtin/_problems" /tmp/hc-bi/problems
go run ./cmd/hc -w /tmp/hc-bi cases build <slug> --force -l python
```

Rebuild or reinstall `hc` afterwards; the samples are embedded at compile time.

## Conventions

- Pre-1.0 (`v0.x`): no backward compatibility is required for the CLI, `hc.yaml`, the problem protocol or the DB schema. Prefer the cleanest design over migrations or compatibility shims.
- Versioning (details in CONTRIBUTING.md): SemVer tags with a `v` prefix. Fixes to the released line bump the patch (`v0.1.1`) and never change features or the protocol; features for the next milestone ship as pre-releases (`v0.2.0-alpha.N`) until it is done; no `-rc`. Patch releases are tagged on `main` until `main` holds unreleased features, then on a maintenance branch `v0.N.x` created from tag `v0.N.0`: the fix lands on `main` first, then `git cherry-pick -x` through a PR against `v0.N.x`. Never merge or delete a maintenance branch. Pushing a `v*` tag runs `.github/workflows/release.yml` (GoReleaser; `prerelease: auto` marks `-alpha` tags). `hc --version` falls back to the module build-info version for `go install …@vX` builds.
- Commit messages use Conventional Commits (`feat:`, `fix:`, `ci:`, `docs:` …). GoReleaser groups the changelog by these prefixes.
- Imports are grouped std / third-party / `github.com/MorePeanuts/handcoding` (goimports `local-prefixes`).

## Workflow

- Bug reports and feature requests arrive either as GitHub issues or in conversation. Never pick up issues on your own. Work on an issue only when the user names it.
- Before writing code, judge whether the request holds up: confirm the bug reproduces and isn't intended behavior, and check that the feature fits the design and the roadmap. If it doesn't, say so and discuss; don't implement it as written. Issues labeled `needs-discussion` always need this step.
- The roadmap is the GitHub milestones, one per `v0.N.0`. Each description holds the goal, scope and exit criteria, and its issues track the work. Ideas not yet assigned to a release go in the `Backlog` milestone and move to a version milestone once agreed. Keep no roadmap or TODO files in the repo.
- GitHub content (issues, milestones, PRs, templates) is written in English.
- Branching (details in CONTRIBUTING.md): code, CI and substantial doc changes go on a short-lived branch named `<type>/<issue>-<summary>` from an up-to-date `main`, then a PR whose title is a Conventional Commit and whose body says `Closes #N`. Run `make test` and `make lint` before pushing, and wait for CI. Typos may go straight to `main`, and so may anything the user explicitly says to commit to `main`.
- Merging: squash by default (`gh pr merge --squash`); rebase merge only for a series of clean, separately meaningful commits; merge commits are disabled. Merge only when the user says so, then switch back to `main` and pull. Branches are deleted on merge.
