# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`hc` (handcoding) is a Go CLI/TUI that judges LeetCode-style problems locally: users write solutions in their own editor, and `hc` builds, runs and judges them offline, debugs them with Delve/pdb, fetches problems from LeetCode, and delegates test-case authoring to coding agents (Claude Code / Codex). User-facing docs are in English (`README.md`, `docs/`, `CONTRIBUTING.md`); `README_zh.md`, `docs/how-to-use_zh.md` and `docs/protocol_zh.md` mirror them in Chinese; update both languages together.

## Commands

```sh
make build            # bin/hc (version from git describe via -ldflags)
make install          # go install into $(go env GOBIN)
make test             # go test -race ./...
make lint             # go vet + golangci-lint (CI pins v2.15.0, see .github/workflows/ci.yml)

go test ./internal/app -run 'TestRegressionReferences/two-sum' -v   # one subtest
go run ./cmd/hc -w /tmp/hc-dev test two-sum                       # run against a scratch workspace
```

- Integration tests in `internal/app` and `internal/tui` actually compile and run solutions; they need `go` and `python3` (3.10+) on PATH and skip otherwise. Their workspaces set `python.interpreter: python3`, so tests never create a virtual environment or touch the network; `python.Venv` is tested with fake `uv`/`python` scripts on PATH.
- Go ≥ 1.26 is required (`errors.AsType` is used); `go.mod` pins the toolchain version.
- Use a throwaway workspace while developing (`hc init /tmp/hc-dev`, then `-w` or `HC_WORKSPACE`) instead of the user's `~/handcoding`. A new workspace is empty; `cp -R testdata/regression /tmp/hc-dev/packs/` installs the regression set in it as a (read-only) pack. The set is also an authoring workspace of its own (see Regression set); to try one without touching the set, copy it elsewhere and run hc in the copy.

## Architecture

Request flow: `internal/cli` (cobra) or `internal/tui` (bubbletea) → `internal/app` (use cases; the only layer both front ends call) → `internal/runner` → a `lang.Language` driver → `internal/judge`.

**Problem protocol** (`internal/problem`, spec in `docs/protocol.md`: normative, protocol 1; hc's behavior goes in `docs/how-to-use.md`, authoring advice in the skills). A problem is a directory with `problem.yaml` (signature + judge options), `description.md`, `cases.jsonl`, optional `reference/solution.{py,go}` and `templates/`. Types reuse LeetCode's `metaData` names (`integer[]`, `ListNode`, `TreeNode`, `list<T>` normalized to `T[]`) so `internal/leetcode` can import questions without translation. Kinds: `function` and `class` (design problems driven by `ops`/`args`; with `judge.round_trip` a case is instead one value, which the driver passes to the encoder and the resulting string to the decoder, on two instances or one, and only the decoder's result is judged). `judge.output` names the parameter to judge for in-place (`void`) problems, and `judge.output_length: return` limits it to the first k elements. Function problems may also declare *structure inputs* (`internal/problem/structure.go`): `hidden` case inputs the solution never receives, and `cycle` / `join` / `ref` / `copy` parameters that the drivers build from them (list cycles, intersecting lists, nodes referenced by value, deep copies); `returns_ref` encodes a returned node by identity (index in a list, value in a tree). `hc fetch` derives them by comparing metaData (the judge's test data) with the template's signature (`internal/leetcode/structure.go`). *Judge-defined types* (`internal/problem/judgetypes.go`) are the structures LeetCode's judge defines: its six `Node` variants, each with its own protocol type (`GraphNode`, `NaryNode`, `RandomListNode`, `NextTreeNode`, `QuadNode`, `MultilevelNode`) but called `Node` in solution code, plus `NestedInteger` and `Employee`; `returns_copy` makes a deep copy that shares a node with its parameter a runtime error. For these, metaData describes LeetCode's serialized test data, so `internal/leetcode` reads the signature from the Go template instead (`template.go`, the Node variant from the struct in its comment). `judge.compare` has no default: without it a problem is *not ready* (`Problem.Ready`): `hc submit` refuses, and `hc test` shows outputs with the `NotJudged` verdict. Readiness is also per language (`Problem.ReadyFor`, the solution file): a solution is judged only when the problem has a reference in its language, since time limits are to be measured against it; `app.SubmitError` and `NotReadyHint` say which is missing, and `hc validate` reports a language of the pack without a reference (an error under `Strict`). `hc fetch` deliberately leaves it unset, because deciding the judge rule means reading the statement, and that is `hc gen`'s job (the `hc-cases` skill's "decide the judge rule" step). *Locales* (`internal/problem/locale.go`, spec section `locales`): `locales` in `pack.yaml` (BCP 47 tags, the first the default) are the statements' languages; `description.md` and `title` are the default's, `description.<locale>.md` and `titles` (problem.yaml, and the pack's and groups' in pack.yaml) the others'. `Problem.ValidateLocales` requires a statement and a title in every declared locale and none in another; `app.ValidateProblem` and `hc import` apply it. hc translates nothing: `hc fetch` writes the locales LeetCode has (`Converted.Localize`: `content` is `en`, cn's `translatedContent` is `zh-CN`), adds missing ones to a fetched problem from the other site, and `hc gen`/`hc fix` and the skills never write a translation. The TUI (`i`, `internal/tui/locale.go`) and `hc show --locale` choose one; `app.Locale`/`SetLocale` remember it per pack as the pref `locale`, falling back to the default.

**Packs** (`internal/pack`, spec chapter `packs`). A pack is `pack.yaml` plus `problems/<dir>/`; problem identity (slug, id) is per pack. `pack.Load` rejects unknown fields and checks `protocol` before anything else, `Validate` checks the manifest alone and `ValidateProblems` its groups against the pack's problems. The protocol versions (`problem.Protocol`, `problem.MinProtocol`) and the protocol's language ids (`problem.Languages`) live in `internal/problem/protocol.go`; `TestProtocolLanguages` keeps the drivers in `app.Languages` equal to them. hc's version is `internal/version` (set by `-ldflags`), so packages below `internal/cli` can name it in messages. `pack.LoadProblems` loads a pack's problems (setting `Problem.Pack`), and `pack.IdentityErrors` checks a problem's directory name, slug and id against the rest of its pack. `Problem.Ref()` is `pack/slug`, the key of solutions, history and TUI state.

**Embedded spec.** `docs/docs.go` (package `docs`, beside the Markdown because `go:embed` cannot reach parent directories) embeds `docs/protocol.md`, the English and normative text, and `hc docs protocol [section]` prints it (`internal/cli/docs.go`): Markdown when piped or with `--raw`, rendered like `hc show` on a terminal. Section ids are the GitHub anchors of its `##`+ headings (`internal/markdown`: GitHub's slug rule, duplicates numbered, headings in code fences ignored), and a section includes its subsections. Skills cite these ids, so renaming a heading is a breaking change for them; `TestProtocolLinksResolve` checks that every `](#anchor)` in the document names a section.

**Driver protocol** (`internal/lang/lang.go`; documented in CONTRIBUTING.md, "Adding a language"). It is internal to hc and not part of the problem protocol's spec. Language drivers never judge. They read `HC_CASES` (JSON array of `{id,input}`), call the user's code, and append `{id,output,error,elapsed_ns}` lines to `HC_OUT`. All comparison (exact / unordered / unordered_deep / any_of / float tolerance) happens in `internal/judge` on decoded JSON. User stdout/stderr pass through untouched. Missing result lines become RE or TLE in `runner.Run`. Adding a language = implement `lang.Language` and register it in `app.Languages`. Each driver declares `MinVersion`, the oldest toolchain the protocol supports (Python 3.10, Go 1.22): generated code, the regression set's references and pack content must work on it, user code need not. Below it, `hc test`/`submit`/`debug` warn and reference runs (`cases build`, `validate --run`) fail; CI runs Python 3.10 and `TestGoMinimumVersion` vets the Go side at `go 1.22`.

- **Go** (`internal/lang/golang`): each solution dir is a standalone module. `zz_hc_driver.go` = static `runtime.go.txt` (ListNode/TreeNode, codecs, main loop, nil-slice normalization) + `runtime/<Type>.go.txt` for each judge-defined type the problem uses (LeetCode's six `Node` variants are all `type Node` there, so a problem uses at most one) + per-problem `hcCall` generated from the signature. It sits next to `solution.go` so gopls and Delve breakpoints work on the user's real file. `Build` keeps programs in `.hc/cache/build/go/<hash>/` (`Language.BuildCache`), keyed by the module's files and `go env`, and skips a build that is there: besides the build, that saves macOS's 150–270 ms check of every new executable. They are built with `-trimpath`, so a reference's scratch directory reuses the program of a solution with the same files, and `hcStack` names the real `solution.go` from the working directory.
- **Python** (`internal/lang/python`): `hc_runtime.py` (embedded, must stay Python 3.10 compatible) plus a generated `_hc_runner.py` that embeds the signature as JSON. Judge-defined types are classes named after their protocol type; starters and references import them under their code name (`from hc_runtime import GraphNode as Node`), and the codecs read nodes by attribute, so solutions can build their own. Unless `python.interpreter` is set in `hc.yaml`, `app.Languages` gives the driver a `python.Venv` in `.hc/venv`: created on first use (`Language.Setup`, also called lazily by `Toolchain`/`Build`) with `uv venv --python '>=3.10'`, else the newest Python 3.10+ on PATH with `-m venv`; in an authoring workspace with exactly `MinVersion` (`Venv.Version`: `uv venv --python 3.10`, else `python3.10` on PATH, else the newest with a warning), so that pack content runs locally on the Python its CI uses, and an environment of another version is recreated when 3.10 can be had; recreated when its interpreter stops running, or by `hc env sync`. It holds only debugpy, and writes `pyrightconfig.json` at the workspace root if missing. `app.Run`/`RunReference` set it up with the run's stderr, so the TUI shows progress in the run output; `app.Start` does not, because the TUI calls it synchronously.
- Driver files are regenerated by `Prepare` before every run; never hand-edit them in a workspace.

**Checkers** (`judge.compare: checker`, `checker.py` in the problem dir; validated both ways). Problems with many valid answers or random output are judged by `check(input, output, expected)`, written in Python for every solution language. After the driver, `runner.check` sends every case that produced an output to one process via `lang.Checker` (Python's `hc_checker.py`, next to `hc_runtime.py` so checkers can import its codecs), within the run's time limit. `judge.Checked` turns the `{id,ok,message}` lines into verdicts; the message goes into `CaseResult.Message` (report, TUI, history). A checker that fails to load, raises, returns garbage or times out is a `*judge.CheckerError` for the whole run, never a verdict. `app.runnerOpts` requires a supported Python before running, even for Go solutions.

**Generated cases** (`generate` instead of `input` in `cases.jsonl`, `generator.py` in the problem dir; validated both ways; spec section `generators`). Large inputs are built, not stored: a case names a function of `generator.py`, called as `name(rng, **args)` with `rng` the splitmix64 `hc_runtime.Rng` (pinned by `TestRng`, since digests depend on it), and has no `expected`. `runner.Generate` runs them in one Python process through `lang.Generator` (`hc_generator.py`) and checks each input against the case's `digest` (`problem.InputDigest`, sha256 of the canonical JSON); `app.expectGenerated` takes the expected outputs from a reference. `app.Materialize` does both for a run (`Run`, and `hc debug`), preferring the reference in the solution's language, and keeps the results in `.hc/cache/cases/<pack>/<slug>/<lang>.json`, keyed by hc's version, problem.yaml, generator.py, the reference and the generated lines (`cacheKey`), best effort. `BuildCases` writes digests and cross-judges the other references on new or changed ones; `ValidateProblem` with `Run` builds them afresh, never from the cache, and `hc cases list --expand` (`app.GenerateInputs`) builds only their inputs, unchecked against the digests, so that authors (and agents, who cannot import `hc_runtime`) see what generator.py makes. A generator or reference that fails, or a digest mismatch, is a `*runner.GeneratedCaseError` for the whole run. A stored case line over `problem.MaxStoredCase` (100 KB) is a warning, an error under `Strict`. `any_of` cannot judge generated cases.

**Workspace** (`internal/workspace`). Two kinds (`Workspace.Kind`). A *practice* workspace: `hc.yaml` (with `packs:`, the installed packs: `Config.Packs`, `[]PackSource{Name, Source, Ref, Commit}`, no commit for a copied directory; `SavePacks` rewrites only that node through goccy/go-yaml's AST, so comments and order survive), `packs/local/problems/<NNNN-slug>/` (the workspace's own problems), `packs/<name>/` (installed packs), `solutions/<pack>/<lang>/<NNNN-slug>/`, `.hc/hc.db`, `.hc/venv/`, `pyrightconfig.json`. An *authoring* workspace is a pack checkout: `pack.yaml` and `problems/` at the root, `hc.yaml` optional (personal settings only; defaults without it, hc never writes it there, and `Open` rejects a `packs:` or `locales:` key in it), the same `solutions/`, `.hc/`, `pyrightconfig.json` and skills beside them (the checkout's `.gitignore` lists them; `hc pack init` writes it). Discovery order is `-w`, `$HC_WORKSPACE`, then `Lookup` from the working directory (the nearest parent containing `hc.yaml` or `pack.yaml`, except that a `pack.yaml` directory directly in `packs/` of a practice workspace is an installed pack, so the search goes on to that workspace), then `~/handcoding`. A directory with both files is an authoring workspace; `Open` refuses an installed pack, and `Create` (`hc init`) refuses any directory in a pack. `Workspace.Packs` lists `workspace.Pack` values (name, dir, manifest, `Writable`, `Err`), re-read on every call. In an authoring workspace it is the one pack, named by its manifest (by the directory while the manifest fails), dir the root, writable; a broken or newer-protocol `pack.yaml` sets its `Err` rather than failing `Open`, so `hc validate` can report it, and a `packs/` directory there is ignored. In a practice workspace: `local` first, with no `pack.yaml` (the name is reserved) and a synthesized manifest of the newest protocol, every language and the locales of `hc.yaml` (`Config.LocalLocales`, `[en]` when unset), then every other directory of `packs/`, whose `pack.yaml` is loaded (protocol first) and validated before its problems, and must name it after its directory; a pack that fails is listed with `Err` (a `*PackError`) instead of failing the workspace. `WritablePack` (`local`, or the pack itself in an authoring workspace) is where `new`/`import`/`fetch` write; `CheckWritable` makes `gen`, `fix`, `rm` and `cases add|rm|edit|build` refuse installed packs; `hc rm` (`app.RemoveProblem`) also takes the slug out of the groups through `Pack.RemoveFromGroups`, which edits `pack.yaml`'s AST like `SavePacks`. `Problem(ref)` resolves `<pack>/<ref>` within one pack and a bare ref across all (several exact matches are an error listing `pack/slug`); `Ref(p)` is the shortest reference for hints. `app.SolutionLang`/`CheckLang` enforce the pack's `languages` (`Start` and `Run` check too). An `hc.yaml` with a root `problems/` and no `packs/` (and no `pack.yaml`) is the old layout, which `Open` refuses with a message; there is no migration. Code outside the package branches on the kind only to pick the skill context (`skillContext` in `internal/cli`) and in pack management, which needs a practice workspace (`hc pack check` an authoring one).

**Pack management** (`hc pack`, `internal/app/packs.go`; the CLI in `internal/cli/pack.go` only prints). `internal/git` runs the `git` on PATH (no git library): clone (partial, `--filter=blob:none`, for URLs), fetch, resolve a ref (origin's branch, then a tag, then a commit), detached checkout, `status --porcelain`. A source is a git URL, a git repository (cloned, recorded as an absolute path) or a plain directory with `pack.yaml` (copied with `pack.Copy`: `pack.yaml` and `problems/` only; no commit). `InstallPack` stages into `packs/.tmp-*` (dot-dirs are skipped by `Packs`), checks the manifest and the name, renames into `packs/<name>/` and records it; `InstallMissing` reinstalls listed-but-missing packs at their recorded commit. `UpdatePack` refuses local changes unless `--force`, fetches and checks out the ref's commit, undoes an update whose manifest fails or renames the pack, and reports added/removed slugs and `Orphan`s (solutions or history no problem uses now; never deleted). `RemovePack` keeps `solutions/<pack>/` and history unless purge (`store.DeletePack`). These four take `Workspace.LockPacks` (a non-blocking OS file lock on `.hc/packs.lock`, `lock_unix.go`/`lock_windows.go`), which also re-reads the packs list, and `git.Fetch` refreshes `origin/HEAD` so the default branch is followed after a rename. Validation lives in `internal/app/validate.go` (`ValidateProblem`, `ValidateWorkspace`, findings as data); `hc validate` prints it, and `CheckPack` (`hc pack check`, authoring workspaces only) runs it with `Run` and `Strict` (not ready, or a reference that cannot run, is an error). Tests build git repositories in temp dirs (`requireGit` isolates the user's git config).

**Pack scaffolding** (`hc pack init`, `app.InitPack` in `internal/app/packinit.go`). Writes `pack.yaml` (from a struct), `problems/.gitkeep`, and the templates in `internal/builtin/packinit/` (`gitignore`, `check.yml`, `AGENTS.md`, `CLAUDE.md`; `text/template` with `<% %>` delimiters, since workflows use `${{ }}`), then installs `skill.Set(skill.Authoring)`. It checks every path first and writes nothing on a conflict, and never runs git. `check.yml` pins `version.String()` when `app.ReleaseVersion` accepts it, else `@latest`. Guide: `docs/packs.md`. `TestPackInit` (`internal/cli`) lints the hc commands of the generated workflow and agent files like `TestSkillsLint`.

**LeetCode account** (`hc leetcode login|logout|status|test|submit`, `internal/cli/leetcode.go`, `internal/app/leetcode.go`). Runs or submits a solution on the user's LeetCode account. `internal/leetcode/judge.go` extends the fetch client: a `Session` (the browser's `LEETCODE_SESSION` cookie, which `ParseSession` also finds in a pasted Cookie header or cURL command; the client sends a CSRF token it makes, as both the `csrftoken` cookie and `X-CSRFToken`, since LeetCode does not tie it to the session), `Username` (GraphQL `userStatus`), `QuestionMeta` (the internal `questionId`, which differs from the frontend id, and `exampleTestcases`), `Interpret`, `Submit`, and `Wait`, which polls `submissions/detail/<id>/check/`; refusals (401/403, or an HTML page) are `ErrBlocked`, 429 `ErrRateLimited`. Sessions live in `hc/leetcode.json` of `os.UserConfigDir` (0600, per site), never in a workspace; `LeetCodeLogin` saves only a session LeetCode signs in; `hc leetcode login` gets it, as the VS Code extension does, from the site's undocumented `authorize-login/http/?path=<host:port/path>` page, which redirects a signed-in browser there with `?cookie=` (`Site.AuthorizeURL`, `app.StartLeetCodeBrowserLogin`: a server on 127.0.0.1 at a random path, taking one callback), or with `--paste` from a pasted value; `LeetCodeStatus` checks each saved session with `Username`; and `LeetCodeLogout` forgets every site's session unless given sites (`hc leetcode logout` ignores `leetcode.site`, since `test`/`submit` take the site from the problem); tests set `HOME`/`XDG_CONFIG_HOME` and point a `Site`'s `Base` at `httptest`. `app.LeetCodeProblem` takes the site and slug from `source` (its URL, else `source.site`) and refuses other problems. Drivers turn a solution into LeetCode's code through the optional `lang.LeetCoder` (Python drops `hc_runtime` imports and requires `class Solution` for function problems; Go drops `package main`). `app.LeetCodeCase` maps a failed submission's `last_testcase` onto a case of a plain function problem (no structure inputs or judge-defined types) for the suggested `hc cases add`. Results are not recorded in history.

**History** (`internal/store`): SQLite via `modernc.org/sqlite` (pure Go, no cgo). Submissions are keyed by `(pack, slug)`. The schema is created in its final form with no migrations: a `submissions` table missing a column comes from an older hc and `store.Open` fails with `ErrOldSchema` (delete `.hc/hc.db`). `submissions.details` holds the judge report encoded by `app.EncodeReport`. Failing cases are stored with truncated input/output so the TUI can re-render them later. The `prefs` table (`Pref`/`SetPref`, keyed by pack, `""` for the workspace) holds what hc remembers between runs, such as the TUI's last pack, and `stars` (`SetStar`/`Stars`) the problems starred with `m` in the TUI; `DeletePack` removes a pack's prefs and stars too, `DeleteProblem` (discard) neither.

**Expected outputs come from reference solutions, not from the model.** `hc cases build` runs `reference/solution.*` through the same runner and writes outputs into `cases.jsonl`. `hc gen` / `hc fix` (`internal/agent`) run `claude -p --output-format stream-json` / `codex exec --json` as subprocesses in the workspace; `Agent.Run` reads their events (`trace.go`: a progress line per tool call, the final message, Claude's turns and cost) and writes every line it reads, timestamped, between a `start` and an `end` line, to a log that `app.CreateAgentLog` keeps in `.hc/agent/<pack>/<slug>/` (newest `KeepAgentLogs`); a custom `agent.command` is `Text`, shown and logged as it is. Their prompt names the skill it needs through the registry. The presets sandbox the agent's commands to the workspace and temp directories, so `runAgent` sets up every language's environment first and `agentEnv` points `GOCACHE` and `UV_CACHE_DIR` into `.hc/cache/`.

**Agent skills** (`internal/skill`). Sources are `internal/builtin/skills/<name>/` (`SKILL.md` plus supporting files; names start with `hc-`), embedded and read into a registry; `skill.Set` maps a context, chosen by `workspace.Kind`, to the skills it gets, so a new skill or context is a new entry: `Practice` gets `hc-problem` and `hc-cases`, `Authoring` (a pack checkout) also `hc-pack`. `hc init`, `hc skill install` and every command that starts an agent install them into the workspace's `.claude/skills/` (Claude Code) and `.agents/skills/` (Codex), each copy with a `.hc-skill.json` mark (hc version, content hash). `hc gen` and `hc fix` install the workspace's set; `hc skill install` without names syncs to exactly that set (`skill.Options.Exclusive`), also removing marked copies of skills outside it; `hc skill install <name>` installs just those. hc replaces or removes only marked copies, keeps edited ones without `--force`, and writes only the `<!-- hc:begin -->` … `<!-- hc:end -->` index block of `AGENTS.md` (which also sends agents' throwaway files to `.hc/scratch/<slug>/`, a directory per problem so that parallel runs keep apart); since Claude Code does not read `AGENTS.md`, `skill.WriteClaudeFile` creates a `CLAUDE.md` of `@AGENTS.md` when the workspace has none (at the root or in `.claude/`), and never touches one that exists. The `hc gen`/`hc fix` prompts add only what their sandbox refuses (`sandboxRule` in `internal/agent`, which names the problem's scratch directory). Agents follow the skills literally: `TestSkillsLint` (`internal/cli`) fails when a skill mentions an `hc` command or flag that the cobra tree lacks, or links a file it does not ship, so update the skills together with the CLI and the protocol.

**TUI** (`internal/tui`): a screen stack (`list → detail → result`, `history → submission`), under the pack picker (`packs.go`) when several packs have problems and no `--pack`/`--group` was given. The list shows one pack at a time, a tab per pack that has problems or that `--pack` names (no tab bar with one), and inside a pack all problems or one group; the pack shown and each pack's group are remembered with `store.SetPref` (key `pack` workspace-wide, `group` per pack), and one that no longer exists falls back silently. Test and submit run in a background `tea.Cmd`. Only the editor and the debugger take over the terminal (`tea.ExecProcess` / `clearScreenCmd`). The markdown theme must be detected before `tea.NewProgram` starts (`ui.DetectTheme`). Once bubbletea owns stdin, the terminal's background-color reply is swallowed and every render stalls until timeout. `ui.Markdown` caches renderers and output.

**Statement images** (`internal/termimg`): `hc fetch` downloads images into the problem's `assets/`. `ui.Markdown` swaps each `![](...)` for a token, lets glamour render, then replaces the token line with the image drawn as plain text lines. Because the image is ordinary lines of text, it scrolls inside a viewport. With kitty (kitty, Ghostty, and herdr, which re-emits kitty graphics to the outer terminal) those lines are Unicode placeholder cells for an image uploaded once with `q=2`; a reply would arrive as keystrokes. Detection is by environment only: herdr answers graphics queries itself and WezTerm answers them without supporting placeholders, so querying would mislead. With blocks, they are mosaic block characters. After the editor or debugger has used the terminal, `Renderer.Forget` forces a re-upload. Never query the terminal for graphics support once the TUI is running.

## Regression set

`testdata/regression/` is hc's regression set: a pack (`pack.yaml`, name `regression`, plus `problems/`) of test data for hc itself, not shipped in the binary (`hc init` creates an empty workspace). `testdata` keeps the Go tool from compiling the `reference/*.go` files inside it. Tests reach it through `internal/regression` (`Dir`, `ProblemsDir`, `Copy`, and `Install`, which copies it into a test workspace as the installed pack `packs/regression`). Being a pack, the directory is also an authoring workspace, so it may hold a developer's `.hc/`, `solutions/`, `hc.yaml` and skills (its `.gitignore` lists them); tests must never depend on them: `Copy`/`Install` copy only `pack.yaml` and `problems/`, and the other tests read only those. `TestRegressionReferences` (`internal/app`) requires every case to have an expected output (a digest, for a generated one), and requires both the Python and the Go reference to pass. `TestProtocolCoverage` (`internal/regression`) checks the pack is valid and fails, naming the feature, unless some problem uses every type and array of node types (as input and output), kind, compare mode, round-trip `instances`, problem.yaml, pack.yaml and cases.jsonl field (generated cases included), structure input and translated statement (the set's `locales` are `[en, zh-CN]`, and every problem must have both), with the lists derived from `internal/problem`, so a new protocol feature needs a problem of the set that uses it. After changing those cases, regenerate expected outputs in the set itself, opened as an authoring workspace:

```sh
go run ./cmd/hc -w testdata/regression cases build <slug> --force -l python
go run ./cmd/hc -w testdata/regression validate <slug> --run
```

Without an `hc.yaml` there, hc creates `.hc/venv` on first use; to use an existing Python instead, put `python: {interpreter: python3}` in a (gitignored) `testdata/regression/hc.yaml`. `git status` must show only the `cases.jsonl` you meant to change.

## Conventions

- Pre-1.0 (`v0.x`): no backward compatibility is required for the CLI, `hc.yaml`, the problem protocol or the DB schema. Prefer the cleanest design over migrations or compatibility shims.
- Versioning (details in CONTRIBUTING.md): SemVer tags with a `v` prefix. Fixes to the released line bump the patch (`v0.1.1`) and never change features or the protocol; features for the next milestone ship as pre-releases (`v0.2.0-alpha.N`) until it is done; no `-rc`. Patch releases are tagged on `main` until `main` holds unreleased features, then on a maintenance branch `v0.N.x` created from tag `v0.N.0`: the fix lands on `main` first, then `git cherry-pick -x` through a PR against `v0.N.x`. Never merge or delete a maintenance branch. Pushing a `v*` tag runs `.github/workflows/release.yml` (GoReleaser; `prerelease: auto` marks `-alpha` tags). `hc --version` falls back to the module build-info version for `go install …@vX` builds.
- **Protocol versions** (`docs/protocol.md` "Protocol versions", CONTRIBUTING.md). A protocol change is anything the spec defines: the fields of `problem.yaml`, `pack.yaml` and `cases.jsonl`, types, kinds, compare modes, structure inputs, judge rules, generators and checkers, the solution ABI, solution languages. A version is a draft until a stable hc release (not `-alpha`) implements it, final from then on (`problem.FinalProtocol`). While `problem.Protocol` is a draft, a change goes into it: mark new features with its number in the Since columns. Once it is final, a change needs a new version: bump `problem.Protocol`, mark the feature with the new number, add a row to the spec's version table (both languages); a change that alters or removes what a final version means also raises `problem.MinProtocol`. `TestFinalProtocol` (`internal/regression`) fails when a final version's features are added to or removed, but cannot see changed meanings, so check those yourself. Releasing a stable version makes its draft final (CONTRIBUTING.md has the steps).
- Commit messages use Conventional Commits (`feat:`, `fix:`, `ci:`, `docs:` …). GoReleaser groups the changelog by these prefixes.
- Imports are grouped std / third-party / `github.com/MorePeanuts/handcoding` (goimports `local-prefixes`).

## Workflow

- Bug reports and feature requests arrive either as GitHub issues or in conversation. Never pick up issues on your own. Work on an issue only when the user names it.
- Before writing code, judge whether the request holds up: confirm the bug reproduces and isn't intended behavior, and check that the feature fits the design and the roadmap. If it doesn't, say so and discuss; don't implement it as written. Issues labeled `needs-discussion` always need this step.
- The roadmap is the GitHub milestones, one per `v0.N.0`. Each description holds the goal, scope and exit criteria, and its issues track the work. Ideas not yet assigned to a release go in the `Backlog` milestone and move to a version milestone once agreed. Keep no roadmap or TODO files in the repo.
- GitHub content (issues, milestones, PRs, templates) is written in English.
- Branching (details in CONTRIBUTING.md): code, CI and substantial doc changes go on a short-lived branch named `<type>/<issue>-<summary>` from an up-to-date `main`, then a PR whose title is a Conventional Commit and whose body says `Closes #N`. Run `make test` and `make lint` before pushing, and wait for CI. Typos may go straight to `main`, and so may anything the user explicitly says to commit to `main`.
- Merging: squash by default (`gh pr merge --squash`); rebase merge only for a series of clean, separately meaningful commits; merge commits are disabled. Merge only when the user says so, then switch back to `main` and pull. Branches are deleted on merge.
